# 用户选择候选点数量设计

## 背景

当前搜索流程固定筛选并计算最多 20 个候选点。结果页虽然可以切换显示
5、10、15 或 20 个地点，但后端已经提前计算了全部候选点的 A、B 路线，
因此该控件不能缩短首次搜索时间。

## 目标

让用户在搜索前输入希望返回的候选点数量，并让后端只筛选、计算和缓存
对应数量的地点。允许范围为 1–20，默认值为 20。

## 前端交互

在主搜索表单的搜索按钮上方增加“候选点数量”数字输入框：

- 使用 `input type="number"`。
- `min="1"`、`max="20"`、`step="1"`，默认值为 `20`。
- 搜索请求新增 `candidate_count` 字段。
- 输入为空、非整数或超出范围时，不发送搜索请求，并展示中文错误提示。

结果页删除现有“显示 5/10/15/20 个”下拉框。结果数量由搜索前的输入决定，
避免两个数量控件表达相近但实际含义不同。

## 后端契约

`POST /api/v2/search` 新增可选字段：

```json
{
  "candidate_count": 8
}
```

本地 Flask 入口和上线 FastAPI 入口都遵循以下规则：

- 字段缺失时使用 20，兼容旧客户端。
- 只接受整数 1–20；布尔值不视为整数。
- 非法值返回 HTTP 400 和
  `候选点数量必须是 1 到 20 之间的整数`。
- 合法值贯穿搜索流水线，并覆盖 LLM 计划中的 `top_n`。
- `filter_and_rank_pois` 仍保留最大 20 的内部保护。
- Session 和搜索响应保存、返回 `candidate_count`，便于调试和前端确认。
- 路线重算复用 Session 中既有的候选点集合，不改变候选点数量。

## 数据流

1. 用户输入候选点数量并发起搜索。
2. 前端发送 `candidate_count`。
3. API 在调用 LLM 或高德之前完成类型和范围校验。
4. `run_pipeline` 使用该值筛选基础 POI。
5. 后端仅为这些 POI 计算 A、B 路线和路径缓存。
6. 初始响应返回实际候选点列表及 `candidate_count`。

## 测试

自动化测试覆盖：

- 缺省值为 20。
- 接受 1 和 20 两个边界值。
- 拒绝 0、21、小数、字符串和布尔值。
- 用户值覆盖 LLM 返回的 `top_n`。
- Flask 搜索接口在流水线执行前拒绝非法值。
- 上线适配层保留同一校验和流水线契约。
- 前端读取数字输入并将其加入搜索请求。

浏览器验证覆盖：

- 默认显示 20。
- 输入合法数量后，结果数量和路线计算数量一致。
- 非法输入会在前端提示，且不发起搜索。

## 范围外事项

- 不改变高德单次 POI 搜索返回量。
- 不在结果页动态增加已被后端省略的候选点。
- 不修改现有 Session TTL、路线绘制或中点计算逻辑。
